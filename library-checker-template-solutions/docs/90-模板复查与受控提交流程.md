# Library Checker 模板复查与受控提交流程

> 本文规定如何按章节枚举 Library Checker 官方题目，用参考实现复查并订正用户模板，从订正后的模板生成独立提交源码，并完成本地与在线验证。代码风格、公共能力复用和测试要求仍以 `../hushuqi算法竞赛模板/编写规范.md` 为最高约束。

这套流程的目标是验证和改进用户模板，不是让参考代码取得 AC。参考实现只用于理解算法、发现错误和比较性能；最终被验证、提交的代码必须来自修改后的用户模板。

过去误交参考源码的根因不是“提交前没有算哈希”，而是最开始就选错了候选源码。即使一份参考代码能够编译、通过本地测试且哈希始终一致，它仍然不能验证用户模板。因此本流程把“来源身份门”放在正确性、性能和在线提交之前。

## 流程反思与不可重复的错误

此前复查第 04 至第 08 章时，执行者只检查了模板正文、头文件和现有测试，然后从当前 `manifest.json` 中没有找到这些章节的候选，便报告“没有可提交源码”。这个结论倒置了因果：`manifest.json` 只记录已经生成的候选；候选为零说明尚未做官方题目反向映射和源码生成，不能说明该章没有对应 LC 题，更不能据此结束章节。

那次执行具体漏掉了四件必须完成的工作：

1. 没有从冻结的官方题库枚举 `string`、`graph`、`tree`、`number_theory` 和 `enumerative_combinatorics` 全集；
2. 没有逐道建立“官方题目 -> 章节条目”的映射，并在章节缺项时按编写规范补入模板；
3. 没有在每题参考实现对照和模板订正后，从当前模板生成对应的唯一 `main.cpp`，也没有加入 `manifest.json` 与逐题元数据；
4. 没有进行逐题在线提交，却把章节测试通过当作章节复查完成。

以后遇到“某章当前候选为零”时，唯一允许的结论是“该章 LC 闭环尚未开始或尚未完成”。必须继续枚举官方题、建立映射、补模板、生成候选、登记清单和在线验证，不能把空清单解释为没有任务。

## 所有章节的 LC 反向覆盖基线

### 映射表前置门

用户给出章节编号后，不允许先从 `manifest.json`、现有题解目录或历史提交猜测题目范围。第一步固定为直接查询 `LC_TEMPLATE_MAPPING.tsv` 的 `chapter` 列，例如第 04 章执行：

```powershell
rg "^04\t" library-checker-template-solutions/LC_TEMPLATE_MAPPING.tsv
```

该命令的全部结果就是本章冻结题集。必须把这个集合逐题带入参考审阅、模板订正、独立源码生成、本地验证和在线提交，不能因某题没有 `main.cpp`、没有收据或没有历史提交而删掉。存在缺口时，`不可完全置信清单/chapter-04.md` 只提供未完成状态视图，不能代替 TSV 定义范围。

在冻结章节范围或读取现有 `*_AUDIT.md` 之前，必须先执行

```powershell
python library-checker-template-solutions/tools/check_lc_template_mapping.py
```

并以 `LC_TEMPLATE_MAPPING.tsv` 作为唯一的“模板章节/条目 -> LC 唯一题目 ID”路由表。每个官方 `<category>/<problem>` 在映射 TSV 中恰好出现一次：模板条目可以对应多题，但一题不得分配到两个模板位置。发现题目没有真实模板接口时，覆盖矩阵必须保留 `template_gap`，不得用相近条目冒充映射，也不得因尚无候选而从范围中删去；完成模板修改、测试与源码级复核后才可补入 TSV。映射表的 `audited`/`classified` 字段只说明路由证据强度，绝不等价于生成、本地验证或在线 AC。

每次章节开始、模板或候选变化、取得本地收据或线上判定后，还必须运行 `python library-checker-template-solutions/tools/refresh_untrusted_inventory.py`。生成的 `不可完全置信清单/` 按章节列出映射未审计、当前独立源码缺失或过期，以及当前源码既无正式本地验证、也无同哈希线上 AC 的项目。某行消失表示它已通过映射与源码门，并至少具备这两种当前正确性证据之一；全部项目可信时工具自动删除该目录。目录本身是派生报告，不能手工删行改变状态。此处允许线上 AC 作为事后置信证据，不改变在线提交前必须先取得当前本地收据的门禁。

全章节任务开始、中断恢复和结束时还必须运行 `python library-checker-template-solutions/tools/audit_all_chapters.py`，并以 `docs/96-全章节审计快照.md` 核对每章 TSV 范围、受控参考、当前候选、当前本地收据、当前线上 AC 与矩阵中的完整官方唯一标识数量。之后运行 `--check`，确认快照未被后续操作改变。这个快照只揭示结构和证据缺口，不能代替逐题完整阅读；但它能阻止把裸题名、历史提交、候选数量或全章编译结果误报为逐题闭环。

按章节执行时，应先筛选 TSV 的 `chapter` 列，再进入下文的逐题源码复查。新增官方题、改派章节或补齐映射时，必须先更新 TSV 的唯一归属并使校验器通过，然后才能更新覆盖矩阵、候选和提交清单。

### LC 文档归档

长期流程、映射、审计和工具说明统一放在 `library-checker-template-solutions/docs/`。章节审计文件使用其对应的模板章节两位编号，例如第 03 章为 `03-数据结构审计.md`、第 04 章为 `04-字符串审计.md`；没有单一模板章节归属的通用材料使用 `90+`，并排在所有章节文档之后。根目录、`tools/` 和题目源码目录不得新增散落的 Markdown。

`不可完全置信清单/` 是由工具生成的状态视图；有缺口时保留其 `chapter-NN.md` 文件名，不手工改写，零缺口时整个目录自动删除。空的模板缺口清单不保留；未来发现缺口时，先在本章审计矩阵中登记 `template_gap`，完成模板修订、测试和源码级复核后直接写入 TSV。移动或删除文档时，必须同步更新 Markdown 链接、工具路径、结构化回执路径和测试断言，并运行映射校验、相关工具测试和路径检索。

对冻结的 `official_repository.commit`，必须先用官方题库工作树枚举本章负责分类的直属题目目录：

```powershell
git -C library-checker-template-solutions/.local/library-checker-problems `
  ls-tree -d --name-only <official_repository.commit>:<official_category>
```

官方问题分类先按下表归入主责章节。分类是最低覆盖范围；若一题依赖其他章节的公共能力，仍由主责章节收口并在映射中列出跨章依赖。`other` 必须枚举每道题并按实际算法分配到唯一主责章节，不能把整个分类笼统归为“不适用”。分配时先选择决定答案语义和目标复杂度的核心算法所属章节；仍有多个候选时，选择最终候选所暴露的最外层模板接口所属章节；仍无法区分时选择编号最小的章节，并在 `93-其他分类审计.md` 记录候选、裁决依据和跨章依赖。该文件是 `other` 唯一归属的权威索引，一题只能出现一次，改派章节会使相关覆盖矩阵和批次摘要全部失效。`sample` 中的 `aplusb`、`many_aplusb` 等也是实际官方题，归第 01 章覆盖，不能因为分类名是 sample 而排除。只有 `common`、`docs`、`test`、`.github` 等不含题目目录的基础设施分类可以排除，并须在总审计中记录目录性质和固定 commit 证据。

表中的覆盖矩阵文件名是每章复查必须产出的目标，不表示文件当前已经存在或内容已经完整。文件缺失时，先从固定 commit 的官方题目全集创建并把每行初始化为 `review_pending`；文件存在时也必须反向核对后才能复用。`93-其他分类审计.md` 必须先覆盖该 commit 下 `other` 的全部官方题并完成唯一章节分配；它缺失、commit 不同或仍有未分配/重复分配行时，任何依赖其结果的章节都不能进入 `scope_frozen`。

每章的最终覆盖集合等于表中主责分类的完整题集，再并入 `93-其他分类审计.md` 唯一分配给本章的 `other` 题；`official_problem_count` 和完成率都按合并后的逐题行数计算。`official_categories` 列出合并后实际出现的分类；加入 `other` 只代表包含分配给本章的那些行，不代表把整个 `other` 分类重复计入多个章节。

当前冻结 commit `04c8de378bab67be926325de2871f0babb8e6451` 下，第 04 至第 08 章主责分类分别有 `string=12`、`graph=38`、`tree=20`、`number_theory=26`、`enumerative_combinatorics=17`，合计 113 道官方题。这个 113 是尚未计入 `other` 分配题的最低基线，不是五章最终总数。此前报告“第 04–08 章没有候选”至少意味着这 113 道题尚未完成反向映射、模板补缺、独立源码生成和在线验证，而不是没有可做的 LC 题；分配给这些章节的 `other` 题也必须额外闭环。题库 commit 变化后必须重新枚举并更新数量，不能沿用这组快照数字。

每次复查一个章节，都先枚举该行主责分类的全集，再并入 `93-其他分类审计.md` 分给本章的题；合并后的集合才是该章 LC 复查的唯一覆盖基线，`manifest.json`、已有题目目录、参考目录、当前源码数量和本轮提交列表都不能缩小它。官方题的唯一标识固定为 `<official_category>/<problem_name>`，不能只用可能跨分类重名的题目名。为每个官方题建立一行覆盖矩阵，至少记录该唯一标识、具体模板 Markdown 条目与公开接口、同步头文件、公共依赖、模板测试、参考源码、当前 `main.cpp` 路径、来源证据、本地状态、提交编号和在线状态。一个模板条目可以覆盖多道官方题，但不能反向遗漏任何官方题。

每个官方题在本章覆盖矩阵中恰有一行；按状态拆分成多个表时，题目仍只能出现一次。字段值尚不存在时必须写 `null`，不能省略该行或用泛化名称代替：`review_pending` 的映射、头文件、测试、参考源码、候选路径和来源证据均为 `null`；本地参考目录和固定官方题库都找不到可审计实现时为 `reference_gap`；`template_gap` 的模板映射为 `null`；已发现模板必须修改但尚未完成修改、测试和重新审阅时为 `template_change_required`；`source_gap` 必须已经写出具体模板条目、接口、头文件、测试、参考源码和映射证据，但当前候选路径为 `null`；题目标识无法被当前 manifest、验证器或提交器唯一表达时为 `tool_gap`。模板侧的 `not_applicable` 不混入官方题表，另以“模板条目、在本章最终官方覆盖集合中没有独立映射的理由、审阅证据”三列维护在同一文档的模板专属表中。它只说明本章范围结论，不得声称其它主责章节没有同名或可复用的 LC 题；已确认的跨条目复用应单列为共享覆盖。

只有完成按源码顺序的逐题审阅，明确核对题面 I/O、约束、接口前置条件、核心不变量和时间/空间复杂度均由所列模板调用链满足，才可把官方题从 `review_pending` 改为映射或 gap 状态。名称相近、能通过部分样例、需要未记录的改写、或未核对官方规模与内存限制都不构成真实映射。

矩阵中的状态含义固定：未完成源码级对照时是 `review_pending`，缺少可审计的只读参考实现时是 `reference_gap`，章节中没有真实模板实现时是 `template_gap`，已确认现有模板需修正时是 `template_change_required`，已有真实映射但尚无当前自包含候选时是 `source_gap`，当前工具无法唯一表达或处理该题时是 `tool_gap`；这些状态都表示工作未完成。出现 `reference_gap` 时保留该官方题并停止其模板结论：优先从固定 commit 下的官方 `sol/correct.cpp`，或具有固定 URL/commit、许可证和源码 SHA256 的公开 AC 实现，补齐 `library-checker-solutions/<category>/<problem>/main.cpp` 及其 `meta.json` 来源记录；只有第一棵参考目录形成受控快照后才能继续。补齐后必须重新冻结并从头重做该题对照，不能拿候选自身充当参考，也不能直接从网络临时内容生成批次。`not_applicable` 只允许以模板条目为主键，表示该条在本章最终官方覆盖集合中没有独立映射；它绝不能用于任何官方 LC 题，也不能断言其它章节没有等价题。某道官方题需要的能力不在主责章节时，必须先完整阅读 `编写规范.md`，再把该能力补充到主责章节或明确的公共依赖中，并同步 Markdown、头文件与测试；不得以无关题、泛化名称、参考 solver、当前没有候选或“无法建立调用链”为由跳过。

本流程区分三种结论：反向映射完整要求本章官方全集没有 `review_pending`、`reference_gap`、`template_gap` 或 `template_change_required`；当前源码完整在此前提上还要求没有 `source_gap` 或 `tool_gap`，且每题的 `main.cpp`、`meta.json` 均已生成并进入 `manifest.json`；章节 LC 闭环完成在此前提上还要求每题当前状态均为 `online_ac`。单题可以在本章其他行尚未完成时先走完整闭环，但章节不得提前标记完成，最终报告必须列出全部未完成行。

## 一题多实现的附加验证

`LC_TEMPLATE_MAPPING.tsv` 和主 `manifest.json` 继续保持每道官方题唯一主责条目、唯一当前 `main.cpp`；这条唯一性只解决章节路由与主候选身份，不表示同一道题只能验证一个本地模板。全目录复查还必须反向检查：一个官方题若存在多个本质不同、满足完整题面约束的用户模板实现，每个实现都应建立独立变体证据，不能因为主候选已经 AC 就跳过其他实现。

附加变体统一登记在 `variants.json`，源码与元数据放在原题目录的 `variants/<variant_id>/` 下。每个变体独立记录模板条目、语言、源码路径、SHA256、本地官方 checker 收据和线上尝试；它不得覆盖主候选、不得改写 251 题主映射，也不得用另一个已 AC 算法替换被验证实现的核心步骤。共享同一底层实现的别名、转发条目或仅配置差异不重复提交。

纳入前必须逐项核对官方最大规模、时间和空间复杂度、输出证书能力及接口前置条件。只能通过小数据、最坏复杂度不满足约束、内存上界不成立或无法从公开接口输出题目所需证书的实现，列入多实现审计的排除表并写清理由，不生成可提交变体。线上 TLE、WA、RE 等终态如实保留，不能写成正确；本地 checker 通过也不能替代线上 AC。

变体按以下顺序执行：确定性生成、`verify_variants.py --only <variant_id>`、`submit_variants.py --only <variant_id>`。线上仍一次只发送一个变体并等待终态；源码变化后原收据和原在线结果失效。多实现扫描和结果汇总见 `97-多实现在线验证审计.md`。

## 执行总览

### 持续执行约束

当用户要求连续执行多个章节或指定“完成全部要求章节后才能停下”时，执行者必须持续推进冻结范围内的后续工作，直到全部指定章节达到本文件的章节完成标准。中间的进度报告、审计快照刷新、认证健康检查、人工登录请求、单题失败诊断或某章暂未完成，都不是结束任务的理由；它们只决定当前应继续完成哪一项门禁或修复。唯一的例外是 `submission_unknown`：未能唯一定位服务端提交时，不得自行重交，必须依第九节取得用户对该题该次重交的明确许可；在等待该许可期间，仍可继续进行不发送重复请求的诊断、证据核对和模板修复。

1. 按章节表冻结“主责分类全集 + `93-其他分类审计.md` 分配题”并建立覆盖矩阵，再冻结当前单题的模板、依赖、测试、参考实现、工具和官方题库版本；
2. 逐题按源码顺序完整阅读官方题面与 checker、`library-checker-solutions/` 受控参考、当前模板真实调用链和测试；参考缺失时进入 `reference_gap`，先补齐第一棵参考目录并重新从步骤 1 开始；
3. 完整审阅后再作模板结论：没有满足题意、约束和复杂度的接口则进入 `template_gap`，已有实现存在错误或需优化则进入 `template_change_required`；两种情况都先完整阅读编写规范，再订正 Markdown 权威模板并同步头文件、测试和公共依赖，然后重新从步骤 1 冻结并完整审阅。发现同一目标存在复杂度更优的实现时，先比较接口、适用前提、常数、实现长度和可维护性：旧实现仍有独立适用场景或更适合小规模/教学时，必须保留旧接口并新增更优接口，正文写明二者的选择条件和严格复杂度；只有旧实现被新实现严格支配、没有独立价值时才可删除。不得为了线上题通过而悄悄用更优实现覆盖旧接口，或以保留旧版为由不补足官方约束所需的新接口；
4. 只有重新审阅确认当前实现正确后，才能记录 `template_unchanged` 或 `template_fixed` 及逐项依据，随后立即从当前用户模板生成或刷新唯一自包含 `main.cpp`，生成 `meta.json`，加入 `manifest.json`，并完成确定性生成证明或两次独立人工来源复核；
5. 对最终 `main.cpp` 做本地正确性、官方 checker 和同环境性能验证；若当前工具不能用官方唯一标识无歧义地选择该题，进入 `tool_gap`，修复并测试 manifest、验证器和提交器后重新执行本地与性能门；
6. 为当前单题生成可重算的批次 JSON 与 SHA256。默认进入 `direct_authorized` 并提交该题；只有用户明确要求本章、本批或本题提交前确认时才进入 `approval_pending`；
7. 每题取得最终可认证 AC 后才处理下一题；任一失败、哈希不符、未知状态或工具异常立即停止后续在线提交并回到模板订正、重新生成和重新验证。这里的“停止”只禁止跳过失败题或继续发送后续题，绝不允许中止诊断、修复或用户要求的章节/全章节任务；未知结果重试仍须另获明确指示；
8. 只有本章最终覆盖集合的全部题都完成参考对照、模板补缺或订正、独立源码生成与登记，并取得当前 `online_ac`，才能报告该章完成。

## 默认直接提交与显式审批登记

用户已明确规定：Library Checker 在线提交默认无需逐批征求同意。任何章节或题目在真实映射、模板订正、当前独立源码、来源证明、SHA256、本地收据、官方 checker、模板与题目测试、性能结论、工具和官方题库版本全部通过后，进入 `direct_authorized`，执行者应直接逐题提交并等待最终 verdict。

只有用户明确说“本章/本批/本题提交前要经过我同意”时，指定范围才切换为显式审批模式，对应候选必须停在 `approval_pending`，直到用户批准当前单题批次 SHA256。审批要求不得从旧对话、习惯或执行者偏好中推断；未收到明确审批要求时，不能以“尚未获得同意”为由停止已通过全部门禁的正常提交。

默认直接提交不允许跳过任何技术门禁，也不允许批量并发发送。线上始终一次提交一题并等待最终 verdict；出现非 AC、哈希不符、`submission_unknown`、认证异常或工具失败时立即停止后续发送，并按第十节继续处理当前题。由于未知请求可能造成重复提交，`submission_unknown` 无法定位到唯一服务端提交时，重试该题仍须用户明确许可。

认证使用受控 Chromium 持久 profile 中的 Firebase 登录态。提交器必须先无头、只读地提取并检查既有 JWT；令牌仍有效时不得弹出登录窗口或要求用户按回车。只有不存在有效令牌、令牌即将过期或登录态读取失败时，才打开登录页请求用户完成一次登录。令牌不得写入仓库、批次 JSON、收据、日志或源码。

### 认证会话、互斥与恢复

认证是章节线上阶段的共享前置条件，不是每道题都要让用户重复完成的步骤。受控 profile 的唯一位置固定为 `library-checker-template-solutions/.local/yosupo-profile/`；不得为不同题目、不同重试或不同终端创建第二个 profile，也不得在每题结束后删除该目录。题目仍按“一题一命令、一题一最终 verdict”提交，但每个命令只可无头检查和复用同一 profile 中的有效登录态，不能把新的可见登录窗口当成正常逐题流程。

进入一个章节的线上阶段前，执行者必须先做一次无头认证健康检查。健康检查成功后，后续单题提交继续从同一 profile 读取短期令牌；令牌只存在当前提交进程内存，浏览器 profile 继续保存正常网站登录态。一次健康检查失败只允许转入一次人工登录：打开这一个受控 profile 的可见登录页，等待用户完成登录，关闭窗口后立即重新做无头健康检查。重新检查仍失败时，停止线上阶段并报告认证故障；不得对后续题目反复弹窗、反复要求按回车或创建临时 profile。

同一时刻 profile 只允许被一个 Playwright/Chromium 进程占用。启动认证前先确认没有其他提交器、登录辅助脚本或 Chromium 进程以该 profile 为 `--user-data-dir` 运行；如确有活进程，等待该任务结束，不能并发打开。若浏览器异常退出留下 `LOCK` 等锁文件，只有在按实际命令行确认没有进程占用该 profile 后，才可移除该单个陈旧锁文件并重新进行无头健康检查；不得按名称批量结束浏览器进程，也不得删除整个 profile 来规避锁冲突。

认证失败、profile 被占用、无头读取异常和人工登录完成后令牌仍无效都属于线上阶段阻断，而不是“再登录一次就继续”的普通状态。它们必须记录为工具/认证异常，先修复会话复用链并用一次真实的无头复用验证，再恢复提交。每次真实登录都要在最终报告中记录触发原因和是否成功复用；不得记录账号、令牌、Cookie 或页面内容。

## 一、两个题解目录与四种代码身份

仓库中的两棵题解目录职责固定，不能互换，也不能再建立第三棵提交源码目录：

- `library-checker-solutions/` 保存 LC 参考与历史源码，只用于逐题对照算法、边界、复杂度和性能；其中的代码永远不是用户模板的提交候选；
- `library-checker-template-solutions/` 保存从用户模板生成的当前可提交源码、逐题元数据、本地验证器和受控提交工具；对应题目的 `<category>/<problem>/main.cpp` 是本地验证与在线提交的唯一候选。

覆盖矩阵中每道已经确认真实调用链的官方 LC 题目，都必须完成一次独立的逐题闭环：

1. 冻结用户模板条目、公共依赖、模板测试、LC 题面与 checker，以及 `library-checker-solutions/` 中的对应参考源码；
2. 完整对照题目语义、用户模板实现和参考实现，结论落到具体公开接口与边界；
3. 对照结束后，无论结论是 `template_unchanged` 还是 `template_fixed`，都从当前用户模板生成或刷新 `library-checker-template-solutions/<category>/<problem>/main.cpp`，不得复制参考 solver；
4. 对这份最终 `main.cpp` 完成本地编译、模板回归、固定/边界/随机用例、官方 checker 和必要的性能检查；
5. 生成包含题目名、模板映射、源码 SHA256、来源证据和本地结果的批次报告，默认进入 `direct_authorized`；用户已明确要求本范围提交前确认时进入 `approval_pending`；
6. `direct_authorized` 可直接逐题运行线上 `--submit`；`approval_pending` 只有在用户批准报告中的当前批次 SHA256 后才可提交。两种模式都必须等待该题最终 verdict 后再决定是否继续下一题。

这里要区分两种“LC 测试”：`verify_local.py` 使用本地官方题库和 checker，属于生成报告前的只读验证；`submit_yosupo.py --submit` 会向 LC 发送源码，属于通过全部技术门禁后按默认直接提交或显式审批模式执行的在线验证。官方 LC 题在完成源码级对照前必须保留 `review_pending`，缺少受控参考时为 `reference_gap`，没有真实调用链时为 `template_gap`，现有模板必须修正时为 `template_change_required`，已有调用链却尚未生成当前源码时为 `source_gap`，工具无法唯一选择时为 `tool_gap`。只有模板条目没有官方等价题时才可标为 `not_applicable`。不得拿无关题目凑数、生成无关源码、请求无关提交或以“无法建立调用链”跳过官方题。

| 身份 | 位置 | 允许用途 | 禁止事项 |
|---|---|---|---|
| 用户模板 | `../hushuqi算法竞赛模板/` 的 Markdown、同步头文件和测试 | 唯一需要被审阅、修正和长期维护的实现 | 不得只改独立题解而绕过模板 |
| 当前独立源码 | `<category>/<problem>/main.cpp` | 本地编译、官方 checker 验证和在线提交的唯一文件 | 不得引用本地 `.hpp`，不得混入参考 solver |
| 参考实现 | `../library-checker-solutions/<category>/<problem>/main.cpp` | 只读研究数学、算法、边界、复杂度和常数 | 其 AC、哈希和源码都不能证明用户模板正确 |
| 官方测试资产 | `.local/library-checker-problems/` | 读取题面配置、生成器、`correct.cpp` 和 checker | 官方 `correct.cpp` 只能生成期望答案，不能成为提交候选 |

必须特别注意：现有脚本能证明“同一个 `main.cpp` 被本地验证并原样提交”，但不能自动证明“这个 `main.cpp` 确实由用户模板生成”。`meta.json` 中的 `provenance.kind` 只是声明，不是来源证明。因此来源追溯是独立于哈希校验的硬门禁。

现有脚本不能判断当前范围采用默认直接提交还是用户明确要求的审批模式，且批量任务不是遇到首个失败就自动停止。来源身份、授权模式和高风险 canary 都必须由本流程主动核对，不能因为脚本能够继续运行就跳过。

## 二、状态与回退规则

每道题分别经过以下状态；章节汇总状态取其中最早、最弱的一项，不能用部分题目的 AC 覆盖其他题目的失败：

```text
review_pending -> scope_frozen
scope_frozen -> reference_gap
reference_gap --补齐受控参考并重新冻结--> scope_frozen
scope_frozen -> reviewed
reviewed -> template_gap 或 template_change_required
template_gap 或 template_change_required --完整阅读编写规范并修改模板、头文件和测试--> scope_frozen
reviewed -> template_unchanged 或 template_fixed
template_unchanged 或 template_fixed -> source_gap --生成并登记--> standalone_generated
template_unchanged 或 template_fixed --刷新已有候选并登记--> standalone_generated
standalone_generated -> local_verified
local_verified -> performance_reviewed
performance_reviewed -> tool_gap
tool_gap --修复并测试选择链--> standalone_generated
performance_reviewed -> direct_authorized
performance_reviewed -> approval_pending
direct_authorized --发送并取得提交编号--> submitted
direct_authorized --发送结果未知--> submission_unknown
approval_pending --用户批准、发送并取得提交编号--> submitted
approval_pending --用户批准但发送结果未知--> submission_unknown
submitted -> online_ac

submission_unknown --仅定位到唯一的同次服务端提交--> submitted
```

- `local_verified` 只表示本地检查通过，不等于 AC。
- `direct_authorized` 是默认授权模式，但只有候选来自当前用户模板，且来源证明、当前 SHA256、模板与题目测试、本地收据、官方 checker、性能门、工具与官方题库版本均已重新核对并写入报告后才能进入；缺少任一技术门禁时留在相应的未完成状态，不能提交。
- `approval_pending` 只在用户已经明确要求指定范围提交前确认时使用。此状态必须停止在线操作并等待用户批准当前批次 SHA256，不能提前认证或运行 `--submit`。
- `submitted` 只表示服务器返回了提交编号，不等于通过。
- `submission_unknown` 表示请求可能已经到达服务器，但客户端没有拿到可确认的提交编号；该状态既不是失败，也不允许直接重交。
- `tool_gap` 表示 manifest、验证器或提交器不能用官方唯一标识无歧义地选择该题；修复工具前禁止把裸题名映射到猜测的分类或发送请求。
- 只有最终 verdict 为 `AC`、`is_latest=true`，且服务端源码 SHA256 与当前 `main.cpp` 相同，才能进入 `online_ac`。
- 模板、独立源码、清单、测试、验证/提交脚本、LC 映射或官方题库 commit 任一变化，旧批次摘要和已有批准立即失效，必须重新生成、验证并报告。源码、测试、清单或官方题库变化还会使对应本地收据失效。当前生成器重新生成的 `main.cpp` 若字节哈希未变，服务端已经认证的同一源码 `AC` 仍有效；但它不能代替新的当前生成证明和本地收据。只有 `main.cpp` 哈希改变，旧在线结果才不能认证新候选，必须重新走性能门和在线提交。默认直接提交模式在重新通过全部门禁后可进入新的 `direct_authorized`，审批模式则须重新等待当前批次批准。
- CE、WA、RE、TLE、MLE 或显著性能回退都返回模板修改阶段；不得只修题目目录中的 `main.cpp`。
- 已取得提交编号后发生网络、排队或轮询超时，保持 `submitted` 并继续查询原编号；未取得编号但请求可能已经发出时进入 `submission_unknown`，不能把未知结果当失败后盲目重交。

这些状态是复查流程用语，不要求全部写进 `meta.json`。

## 三、逐题复查

### 1. 冻结本批范围

先冻结固定 commit 下本章“主责分类全集 + `93-其他分类审计.md` 分配题”的最终覆盖集合及矩阵。线上或本地可以逐题推进，但 `manifest.json` 只表示当前候选集合，不能定义或缩小覆盖范围。每一行必须显式处于 `review_pending`、`reference_gap`、`template_gap`、`template_change_required`、`source_gap`、`tool_gap` 或后续的生成、验证、提交状态之一；不能因尚未列入 manifest 而从矩阵消失。若当前分类在 manifest 中为零，必须把最终覆盖集合全部初始化为 `review_pending`，而不是宣布本章没有 LC 题。

随后选定本次要推进的单题，同时保留整章覆盖矩阵，并为该题记录：

- 官方题目名、输入输出和约束；
- 用户模板条目、同步头文件、公共依赖和测试；
- 当前独立 `main.cpp` 及其 SHA256；
- 对应参考源码和历史性能数据；
- 本轮准备检查或修改的公开接口。

同时记录用户模板输入、公共依赖、参考源码、验证脚本和提交脚本的当前 SHA256，并确认官方题库位于清单指定 commit、工作树无本地修改。它们共同构成本轮冻结快照。

只有已经生成并登记的题目才属于当前提交批次；但清单外的本章官方题仍须保留在覆盖矩阵中并继续处理，不能把它们当作不存在。不能只扫描参考实现后声称已经全部研究，也不能把未逐题阅读的项目批量标成通过。

### 2. 按源码顺序完整阅读

对每道题都必须从头到尾阅读以下材料：

1. 官方题面、约束和 checker 语义；
2. 用户模板正文；
3. 该实现使用的全部公共头和真实调用链；
4. 对应模板测试；
5. 当前独立 `main.cpp`；尚未生成时明确记为 `null`，不能因此跳过；
6. 对应参考实现。

`rg`、符号列表、编译通过和文件名扫描只用于定位，不能作为“已经读过”的证据。审阅记录必须落实到公开函数及其调用链。

### 3. 比较算法而不是比较文件长短

逐项核对：

- 数学定义、公式来源、不变量和逆过程；
- 输入输出、下标、前置条件、无解表示和边界退化；
- 渐进时间、额外空间和适用范围；
- NTT 或其他变换次数、卷积次数和工作区复用；
- 数据布局、内存分配、取模策略、模整数和 I/O；
- 参考实现依赖的题目保证是否也被模板接口保证。

结论只能是以下三类之一：

1. 模板正确且复杂度、限制和常数均可接受，保留当前短实现；
2. 模板正确但存在可证明的性能问题，研究参考思路后修改用户模板；
3. 模板在数学、接口、边界或复杂度上错误，先修复用户模板并增加回归测试。

参考实现不能整份复制进题目 `main.cpp`。如果参考思路更优，必须先按项目命名、注释、公共能力复用和接口规范改造成用户模板的正式实现，再从新模板生成独立源码。已有 `Z`、NTT、卷积、FPS 或 I/O 能完整满足语义时必须复用；保留专用实现时要逐项记录公共接口不兼容之处和基准证据。

若章节中没有能满足官方题语义、约束和复杂度的真实接口，审阅结论不是“无映射后跳过”，而是 `template_gap`。此时必须进入第四节：先完整阅读编写规范，再根据官方题面和参考实现补充用户模板、同步头文件和测试；补齐并重新审阅后才能生成 LC 单文件。只有本章官方全集每一题都完成这一步或确认已有接口，章节的模板覆盖才完整。

## 四、修改用户模板

Markdown 是最终阅读和复制的权威实现，头文件是用于同步、编译和测试的副本。二者不一致时必须先停止生成，查明差异并恢复同步。需要修复或优化时，修改必须落在模板源头，并同步完成：

开始修改任何模板前，必须从头到尾完整阅读 `../hushuqi算法竞赛模板/编写规范.md`，并按其中的代码风格、封装边界、Markdown、公共能力复用、测试与文件组织要求审阅本章正文、对应头文件、公共依赖、测试和相关 LC 单文件源码；该规范与其他材料冲突时以它为准。

1. 修改 Markdown 中最终供阅读和复制的完整实现；
2. 同步对应头文件和聚合依赖；
3. 更新中文参数、成员和返回值说明；
4. 增加能复现本次问题的固定、边界或随机回归测试；
5. 运行相关模板测试和必要的开发期暴力对拍；
6. 重新核对复杂度、公共能力复用和性能取舍。

禁止为了让 Library Checker 通过而只在独立 `main.cpp` 中打补丁。独立源码不是另一套实现，它只是当前模板针对题目接口的自包含展开。

## 五、生成唯一独立源码

每道题完成逐题对照且相关模板测试通过后，无论模板本轮是否修改，都必须生成或刷新：

```text
library-checker-template-solutions/<category>/<problem>/main.cpp
```

生成不能推迟到整章复查结束后再笼统补做，也不能因为模板结论是 `template_unchanged` 就省略。每份 `main.cpp` 必须绑定刚完成的那道题、刚冻结的模板输入和本轮对照结论；若重新生成结果与现有文件相同，也要以字节一致和同一 SHA256 留下证据。生成 `main.cpp` 的同一步必须创建或刷新该题 `meta.json`，并把题目、官方分类、源码路径、源码 SHA256 和元数据路径加入 `manifest.json`；未进入清单的文件不算已生成候选，不能进入本地或在线验证。

生成过程必须满足：

- 中间拼接文件只存在于系统临时目录；
- 题目目录最终只保留 `main.cpp` 和 `meta.json`；
- `main.cpp` 使用 UTF-8 无 BOM、LF 换行，仅包含尖括号系统头且不超过 1 MiB；
- 除输入输出和题目接口适配外，每个算法符号都能追溯到本轮已审阅的模板条目或公共依赖；
- 不建立 `generated/`、`records/`、公共中间头或第二份提交源码；
- 参考代码的哈希只能标成参考基线，不能写成当前 `source_sha256`。

最强的来源证明是：从冻结的模板文件在系统临时目录确定性生成源码，并与题目目录中的 `main.cpp` 逐字节一致。当前工具尚未自动实现这一证明；没有确定性生成器时，必须逐函数人工记录“独立源码符号 -> 模板文件和接口”的映射，不能只依赖 `provenance.kind=template_solution`。

每题的来源记录至少使用以下格式，写入对应专题审计文档或本轮提交前报告，不另建 `records/`：

| 官方唯一标识 | 最终 `main.cpp` SHA256 | 模板输入路径与 SHA256 | 参考路径与 SHA256 | I/O/脚手架职责 | 生成方法 | 独立复核 |
|---|---|---|---|---|---|---|
| `<official_category>/<problem_name>` | `<hash>` | `<逐项列出>` | `<只读基线>` | `<只允许题目 I/O、接口转换和无算法脚手架>` | `<确定性生成命令或逐函数映射>` | `<复核人/代理及结论>` |

来源门只有两种通过方式：

1. 确定性生成：记录生成工具和全部输入哈希，在独立临时目录重新生成，结果与最终 `main.cpp` 字节一致；
2. 当前尚无生成器：两次相互独立的完整复核都确认每个 `template` 块来自冻结模板，并确认所有 `io_adapter` 与 `scaffold` 块不含算法或参考 solver 代码；报告中明确这是人工来源证明。

确定性生成方式必须把生成工具的仓库相对路径和 SHA256 记入来源证据。人工方式必须先把“每个源码块 -> `template`、`io_adapter` 或 `scaffold` 职责；其中 `template` 块 -> 模板文件、接口和 SHA256”的完整映射规范化并计算 SHA256，再由两个互不查看对方结论的复核者分别完整阅读并生成证据摘要；两份摘要各自计算 SHA256，结论都必须为 `matched`。这些哈希、摘要和结论都进入提交前批次身份，不能只在聊天中口头声明。证据可以写在对应专题审计文档、逐题 `meta.json` 或提交前报告中，不为此新建 `records/`；计算证据哈希时只规范化证据对象本身，避免把最终批次哈希写回证据造成循环依赖。若证据写入专题覆盖矩阵，必须先完成证据和矩阵内容，再计算 `coverage_audit.sha256`；由该哈希派生的批次 JSON、批次 SHA256 和提交前报告不得再写回这版覆盖矩阵。

任何无法解释来源的算法代码都会阻断 `standalone_generated`，不能进入本地验证或授权阶段。参考思路若正式进入模板，必须在报告中明确本轮新增或订正了什么、复用了哪些公共接口以及为何采用；不能把“先复制进模板再展开”当成来源审阅。

生成后更新 `manifest.json` 和对应 `meta.json` 的当前源码 SHA256。若 `main.cpp` 的 SHA256 改变，必须将当前在线状态重置为 `local_only` 并清空当前在线 verdict；若当前生成证明、输入或工具发生变化但 `main.cpp` 字节未变，历史服务端对同一 SHA256 的 AC 仍可保留为在线事实，但旧批次、批准和本地收据失效，必须重新取得当前生成证明和本地收据。旧提交始终只留在该题 `meta.json` 中作为历史索引。

生成器必须显式区分只读核验与写入：`--check` 只比较模板展开结果、`main.cpp`、`manifest.json` 和来源元数据，任何情况下都不得改写文件；`--write` 才能刷新候选。禁止以无参数调用、`--help` 或 `--check` 触发写入。`--write` 遇到字节完全相同的候选时必须保留已有 `validation` 和 `submission_attempts`，不得把已认证的当前线上 AC 降级为 `local_only`；候选字节改变时必须失效当前验证状态，但保留历史 `submission_attempts` 供审计追溯。生成器自身改动后先运行其专用回归测试，再执行 `--check`；只有 `--check` 通过才能使用已有候选继续验证或提交。

## 六、本地正确性门

先检查独立源码身份和格式：

```powershell
python library-checker-template-solutions/tools/submit_yosupo.py --dry-run `
  --only <逗号分隔的题目名>
```

`--dry-run` 只检查清单、元数据、源码 SHA256、编码、换行、本地 `include` 和大小，不会编译，也不会证明算法正确。

脚本发生变化时先运行工具单测：

```powershell
python library-checker-template-solutions/tools/tests/test_submit_yosupo.py
python library-checker-template-solutions/tools/tests/test_verify_local.py
python library-checker-template-solutions/tools/tests/test_generate_ch04_lc.py
```

随后直接验证最终 `main.cpp`：

```powershell
python library-checker-template-solutions/tools/verify_local.py `
  --only <同一批题目名>
```

需要为清单中的全部当前题解生成一张全量题目收据时使用：

```powershell
python library-checker-template-solutions/tools/verify_local.py --all
```

`--all` 只遍历 `manifest.json` 中已有的当前候选，不能证明任何章节的官方题目全集已覆盖；执行它之前和报告它之后都必须核对该章覆盖矩阵。当前验证器会直接编译每份 `main.cpp` 和对应模板测试，并为每题选取一个 sample、一个 boundary、一个固定种子 random。官方 `correct.cpp` 生成期望输出，当前 `main.cpp` 独立运行，最后交给官方 checker 判定。Windows/MinGW 的所有本地编译（候选、模板测试、官方 generator、correct 和 checker）统一追加 `-Wl,--stack,1073741824`；Linux 与在线评测不传该 Windows 专用链接参数。当前 manifest 的三类选定用例不是 Library Checker 的完整正式测试集，也不是任何官方分类的全覆盖证据；高风险算法仍需额外的极限、随机对拍和针对性回归测试。

### 局部验证收据与全量收据

局部验证与章节提交收据必须分离管理。验证器在收据身份（schema、manifest、官方 commit、编译配置）一致时会合并旧题记录；但这不等于局部验证已经覆盖章节全集，也不保证旧记录仍对应当前覆盖矩阵。因此局部复验必须显式使用独立路径，例如：

```powershell
python library-checker-template-solutions/tools/verify_local.py `
  --only <单个题目名> `
  --receipt .local/scoped-receipts/<题目名>.json
```

单题收据与全量收据适用范围不同，必须分离管理。单题提交允许使用 `.local/scoped-receipts/<problem>.json`，但该收据的官方 commit、编译配置、当前源码 SHA256、模板测试哈希和三类官方 checker 用例必须全部匹配待提交的唯一题目；提交器在认证前后均重新核验它。scoped receipt 可以记录生成时的 `manifest_sha256` 以便追溯，但其他题的 `meta.json` 线上状态写回而导致全局 manifest 改变，不使未变源码的 scoped receipt 失效。状态工具必须从收据内部 `problems` 键读取题目身份，而非从文件名猜测；同题存在多个 scoped receipt 时，只接受满足上述逐题门禁且 `verified_at` 最新的一份。单题批次 JSON 的 `receipt.path` 必须精确指向该 scoped receipt，批次生成器不得接受它去代表同章其他题或全章完成。

默认 `.local/yosupo-local-verification.json` 只用于明确需要“当前 manifest 全部候选均已本地验证”的全量审计或第 03 章的既有批次工具。生成全量收据前执行 `verify_local.py --all`，并检查其 `problems` 键覆盖当前 manifest 全部候选；这仍不能替代章节覆盖矩阵。全量收据绑定全局 manifest，任一 manifest 变化均须重生成；局部收据绑定其唯一题目的当前源码、测试、编译配置和官方题库 commit，只有这些逐题对象变化才失效。禁止把局部收据的存在解释为章节收据，也禁止用未绑定当前单题的全量旧记录绕过单题本地门。

本地验证前还要确认官方题库工作树干净，生成器、`correct.cpp`、checker 和所需子模块均来自记录的 commit。本地收据必须绑定当前 `main.cpp` SHA256、模板测试哈希、完整编译配置（包括自动 Windows 链接参数）和官方题库 commit；全量收据额外绑定规范化 manifest 哈希。任一对应绑定对象变化都必须重跑；当前脚本尚未绑定模板输入和脚本自身哈希，所以这两项必须进入提交前批次摘要。

## 七、性能门

正确性通过后才能比较性能。参考实现的历史在线时间只作弱信号，正式结论必须满足：

- 用户模板独立源码和参考实现使用同一编译器、优化参数、机器和输入；
- 先预热，再交替运行多轮并记录中位数或稳定区间；
- 同时验证答案或输出哈希，不能只计时；
- 分开观察纯算法内核和包含 I/O 的端到端时间；
- 至少保留五轮有效原始计时，记录中位数和稳定区间；
- 同时记录峰值内存、输入规模、输入哈希、分布、编译器完整版本、编译参数、双方源码哈希和环境；
- 非唯一输出必须交给 checker，不能仅比较输出文件哈希。

每批应在计时前声明输入、轮数和“显著变慢”阈值；多项式现有审计使用 `1.25x`，这只是当前工程门槛，不是普适结论。原始结果的摘要写入对应专题审计文档；为让同一源码的单题批次可重算，可在 `library-checker-template-solutions/.local/ch03-performance/<problem>.json` 保留当前性能 JSON，并在取得最终结果后保留同题的 `.local/ch03-batches/<problem>.json`、`.local/ch03-pre-meta/<problem>.json` 和 `.local/ch03-results/<problem>.json`。这些都是当前本地状态和收据，不保存任何第二份提交源码、参考源码或历史源码；源码变化、收据失效、重跑性能门或重新提交后必须覆盖为当前版本，不能把旧性能 JSON 当作新源码证据。即使短测未超过阈值，只要渐进复杂度更差，也必须研究更优算法或明确记录约束与取舍。

Windows PowerShell 不能用 `Tee-Object`、`>` 或隐式文本管道保存含中文模板路径的性能、批次和结果 JSON：它可能按控制台代码页解码后重编码，令保存文件的规范化 SHA256 与脚本打印值不一致。必须让 Python 工具直接以 UTF-8、无 BOM、LF 换行写入 `.local`，例如：

```powershell
python library-checker-template-solutions/tools/benchmark_ch03.py `
  --only <problem> --output .local/ch03-performance/<problem>.json

python library-checker-template-solutions/tools/ch03_batch_report.py `
  --only <problem> --performance-file .local/ch03-performance/<problem>.json `
  --output .local/ch03-batches/<problem>.json

Copy-Item library-checker-template-solutions/<category>/<problem>/meta.json `
  library-checker-template-solutions/.local/ch03-pre-meta/<problem>.json

python library-checker-template-solutions/tools/ch03_result_report.py `
  --batch library-checker-template-solutions/.local/ch03-batches/<problem>.json `
  --pre-meta library-checker-template-solutions/.local/ch03-pre-meta/<problem>.json `
  --only <problem> --output .local/ch03-results/<problem>.json
```

这里的 `--output`、`--performance-file` 和结果路径都必须解析到 `library-checker-template-solutions/.local/` 内；批次和结果的 SHA256 始终按解析后的 JSON 对象规范化计算，不按控制台输出文本计算。

发现显著差距时，按算法阶数、变换次数、分配次数、数据布局、取模、模整数和 I/O 的顺序逐函数定位，再修改用户模板、重新生成并重走全部门禁。不得用参考源码替换独立源码来取得更快成绩。

若某题在本条性能门和单题批次机制加入前，已经具备严格的当前 `online_ac`（当前磁盘源码、服务端回显源码和 `source_sha256` 一致，最终 verdict 为 AC，`is_latest=true`，提交编号和时间/内存已写入 `meta.json`），补跑当前源码的性能门后保留这次真实在线证据，不为补齐新格式而重复提交。此类历史迁移不得伪造“提交前批次”或“提交后结果”文件；审计表必须明确它缺少的历史产物已经由当前线上认证取代。源码、收据、模板输入或题库版本变化后不适用该例外，必须重新走完整的单题批次与线上提交链路。

## 八、提交前报告与授权模式

每道对应题完成源码生成、本地正确性和性能检查后，必须为该题单独生成完整报告和可重算批次身份。批次严格只含一道题，章节级审批要求只是让本章每个单题批次分别进入 `approval_pending`，不把多题打进同一摘要。这样前一题的在线结果写回覆盖矩阵和 `meta.json` 后，不会使尚未生成的下一题批次或既有多题批准产生歧义。授权只决定是否在发送前等待用户回复，不改变任何技术门禁：默认模式是 `direct_authorized`，报告完成且下列条件全部满足后直接在线提交该题；只有用户明确要求指定范围提交前确认时，才进入 `approval_pending` 并等待当前单题批次 SHA256 的批准。

进入 `direct_authorized` 或等待审批前必须同时满足：

- 该章节及该 LC 题目的模板映射已完成源码级复查；
- 候选由当前用户模板生成，绝不来自参考代码；
- 当前来源证明、`main.cpp` SHA256、模板输入与测试、local receipt、官方 checker、本地正确性、性能检查、验证/提交工具和官方题库 commit 均已重新核对并写入报告；
- 提交器和在线状态正常，且不存在未处理的失败、哈希不符、`submission_unknown` 或工具异常；
- 一次只提交一题，且前一题的最终 verdict 已确认。

两种授权模式下，任一非 AC、源码或服务端哈希不符、`submission_unknown`、工具失败或认证异常都会立即停止后续提交。请求可能已经发出但未能确定提交编号时，不得自行重试；重试仍须用户针对该批次、该题、该次重交明确许可。

章节闭环报告以一个主责章节为单位汇总进度；每次发送前的批次报告则严格对应其中一道题。可以逐题生成并提交，但不能把多个题目放进同一批次，也不能把多个章节混在一起后用部分 AC 宣称某章完成。单题提交前报告至少包含：

- 当前单题的官方唯一标识；
- 每题从用户模板条目到 LC 题目、参考源码和最终 `main.cpp` 的对应关系及对照结论；
- 每题审阅的模板接口和参考源码；
- 修改过的模板、测试和独立源码；
- 每题最终 `main.cpp` SHA256；
- 规范化 manifest SHA256、当前收据 SHA256、模板输入摘要、来源证据、验证/提交脚本 SHA256 和官方题库 commit；
- 固定、边界、随机、官方 checker 和性能结果；
- 当前收据状态与官方题库 commit；
- 固定 commit 下本章最终覆盖集合的官方总数、逐题清单、已映射数、`review_pending`、`reference_gap`、`template_gap`、`template_change_required`、`source_gap`、`tool_gap` 和各在线状态；
- 未解决风险和清理结果；
- 明确写出当前尚未在线提交的单题及其授权模式；`direct_authorized` 写明将直接提交该题，`approval_pending` 写明用户要求审批的原始范围和当前单题批次 SHA256。

批次身份使用以下固定 schema；字段不得省略，不适用的来源字段使用 `null` 或空数组：

```json
{
  "schema_version": 2,
  "official_repository_commit": "<40 位小写十六进制 commit>",
  "chapter": "<两位章节号>",
  "official_categories": ["<本章主责官方分类>"],
  "coverage_audit": {
    "path": "library-checker-template-solutions/<本章覆盖矩阵>.md",
    "sha256": "<小写 SHA256>",
    "official_problem_count": 0,
    "online_ac_problem_ids": []
  },
  "manifest_sha256": "<小写 SHA256>",
  "receipt": {
    "path": ".local/scoped-receipts/<problem>.json",
    "sha256": "<小写 SHA256>"
  },
  "authorization": {
```

`official_problem_count` 是 JSON 整数，示例中的 `0` 必须替换为生成报告时的实际总数。`online_ac_problem_ids` 列出生成报告时本章已完成的全部官方唯一标识，按 Unicode 码点升序；它比单独计数更能防止覆盖矩阵只改状态却未反映具体题目。`problems` 必须恰有一项，`problem_id` 必须等于 `<official_category>/<name>`，并与 `authorization.scope.problem_id` 完全一致；排序和唯一性都以 `problem_id` 为准。每个 `references` 条目同时绑定第一棵参考目录中的源码和元数据；批次中不允许直接填写网络 URL 或 `.local/` 官方工作树路径，外部或官方参考必须先按 `reference_gap` 规则沉淀到参考目录并记录来源、commit、许可证和哈希。`authorization.scope` 固定为示例中的三字段对象，`kind` 只能为 `problem`。`authorization.mode` 只能是 `direct_authorized` 或 `approval_pending`：默认直接提交时使用 `direct_authorized`、`user_confirmation_required=false`；只有用户明确要求当前范围提交前确认时，才使用 `approval_pending`、`user_confirmation_required=true`。用户的批准必须引用由该 JSON 计算出的批次 SHA256，因此批准结果本身不写回批次 JSON，避免自引用。

`problem_id` 是覆盖矩阵和证据的权威身份，但当前 schema 3 manifest、`verify_local.py --only` 和 `submit_yosupo.py --only` 仍按裸 `name` 选择，并要求题目名在整个官方题集中唯一。当前冻结 commit 的 251 道题经枚举没有重名；每次官方 commit 变化都必须重新做全分类重名审计，并把结果写入章节报告。若出现同名，相关行立即进入 `tool_gap`，在 manifest、验证器、收据和提交器全部升级为按 `(category, name)` 选择且工具测试通过前，不得加入歧义清单、不得用裸名运行 `--only`、不得在线提交。

`meta_pre_submit_sha256` 绑定发送前的逐题元数据。在线提交后脚本必须把提交编号和结果写回同一 `meta.json`，所以该文件哈希发生预期变化；写回后立即生成新的覆盖矩阵 SHA256 和下列最终单题结果对象，但不回改已经使用的提交前批次 JSON。若发送前 `meta.json` 与 `meta_pre_submit_sha256` 不一致则批次失效；发送后除规定的在线结果字段外出现其他变化，则不得认证 `online_ac`。

```json
  "source_sha256": "<提交源码 SHA256>",
  "meta_pre_submit_sha256": "<提交前 meta.json SHA256>",
  "meta_post_submit_sha256": "<写回后 meta.json SHA256>",
  "coverage_audit_post_sha256": "<写回在线状态后的覆盖矩阵 SHA256>",
  "meta_change_check": {
    "unchanged_outside_validation_and_submission_attempts": true,
    "submission_attempts_are_append_only": true,
    "submission_attempt_delta": 1,
    "unexpected_json_pointers": []
  },
  "result": {
    "status": "online_ac",
    "submission_id": 0,
    "verdict": "AC",
    "is_latest": true,
    "language": "cpp20",
```

提交前后 `meta.json` 都按解析后的 JSON 比较。顶层除 `/validation` 与 `/submission_attempts` 外必须完全相同；后者必须保留原数组作为前缀，只能在末尾追加本次逻辑发送及其恢复查询产生的记录，不能删除、重排或改写旧项。`submission_attempt_delta` 写实际追加数：正常取得编号的发送为 `1`；发送结果未知后又定位到同一次服务端提交时可以大于 `1`，但所有新增项必须绑定同一 `source_sha256` 和发送时间窗口，且最多出现一个非空提交编号。`/validation` 只允许提交器更新或删除以下键：`checked_at`、`current_source_sha256`、`current_adapter_sha256`、`current_expanded_sha256`、`status`、`current_source_online_verdict`、`current_source_submission_id`、`current_source_time`、`current_source_memory`、`current_source_submission_time`、`current_source_is_latest`、`server_source_sha256`、`note`；其他键必须不变。

最终结果对象的字段一律保留，不得省略。`result.status` 只能为 `online_ac`、`online_failed`、`online_stale`、`submitted`、`submission_unknown` 或 `submission_error`。未取得提交编号时 `submission_id=null`；未取得最终 verdict 时 `verdict=null`、`is_latest=null`；尚无服务端计时、内存、提交时间或源码时，对应的 `time`、`memory`、`submission_time`、`server_source_sha256` 均为 `null`。`submitted` 必须有整数提交编号但 verdict 为 `null`；最终 verdict 状态必须有整数提交编号和字符串 verdict；`submission_unknown` 必须没有可确认编号，否则应转为 `submitted` 并查询该编号。只要实际尝试过发送，`submission_attempt_delta` 必须至少为 `1`；若预检阶段尚未发送便失败，则不生成这个结果对象，只报告技术门失败并使批次失效。

单题完成要求 `meta_change_check` 的两个布尔值均为 `true`、`submission_attempt_delta >= 1`、`unexpected_json_pointers=[]`，新增尝试与 `result` 一致，且 `result` 满足 `online_ac` 全部条件。其他状态仍生成同结构对象并填实际值，但立即停止章节且不能标记完成。最终结果对象使用与批次相同的规范化 JSON 方法计算并打印自身 SHA256；它是写回后覆盖矩阵的派生输出，不得再写入产生 `coverage_audit_post_sha256` 的那版矩阵。

`deterministic_generation` 要求 `generator` 非空、`mapping_evidence_sha256=null`、`reviews=[]`。`argv` 是不含 shell 引号的逻辑参数数组，顺序必须与实际执行完全一致；影响输出的配置文件都列入 `template_inputs`，禁止依赖未记录的环境变量。`manual_double_review` 要求 `generator=null`、`mapping_evidence_sha256` 为完整逐块映射证据的 SHA256，并且 `reviews` 恰有两项；每项固定包含 `review_id`、`evidence_sha256`、`summary` 和 `conclusion`，其中 `conclusion` 只能为 `matched`。两份复核必须独立完成，不能由同一份扫描结果或同一段摘要派生。

确定性生成证据对象固定为：

```json
{
  "schema_version": 2,
  "problem_id": "<official_category>/<problem_name>",
  "source_path": "<最终 main.cpp 的仓库相对 POSIX 路径>",
  "source_sha256": "<最终 main.cpp 的 SHA256>",
  "generator_path": "<生成工具的仓库相对 POSIX 路径>",
  "generator_sha256": "<生成工具的 SHA256>",
  "working_directory": ".",
  "runner": "<运行时名称和完整版本，原生程序填 native>",
  "argv": ["<按实际顺序记录的参数>"],
  "inputs": [
    {
      "path": "<模板、公共依赖、测试或配置的仓库相对 POSIX 路径>",
      "sha256": "<小写 SHA256>"
    }
  ],
  "generated_sha256": "<独立临时目录生成结果的 SHA256>",
  "byte_equal": true
}
```

其中 `source_sha256`、`generated_sha256` 必须相同，且 `byte_equal` 必须为 `true`；规范化该对象所得 SHA256 必须等于批次身份中的 `generation_evidence_sha256`。进入线上阶段前，要用相同工具、输入、工作目录、运行时和参数再次生成并逐字节比较。

人工逐块映射证据对象固定为：

```json
{
  "schema_version": 2,
  "problem_id": "<official_category>/<problem_name>",
  "source_path": "<最终 main.cpp 的仓库相对 POSIX 路径>",
  "source_sha256": "<最终 main.cpp 的 SHA256>",
  "blocks": [
    {
      "id": "001",
      "kind": "template、io_adapter 或 scaffold",
      "start_line": 1,
      "end_line": 20,
      "template_path": "<template 时填写路径，其他 kind 时为 null>",
      "template_sha256": "<template 时填写哈希，其他 kind 时为 null>",
      "template_symbol": "<template 时填写接口，其他 kind 时为 null>",
      "note": "<说明模板对应、题目 I/O 适配或脚手架职责>"
    }
  ]
}
```

`blocks` 按 `start_line` 排序，必须无重叠、无空隙地覆盖最终源码全部物理文本行，`id` 唯一；文件末尾的 LF 是最后一行的结束符，不额外产生空行。`kind=template` 用于来自模板的算法、数据结构和公共实现，必须填写三个模板字段并逐字核对所列接口；`kind=io_adapter` 只允许题目输入、输出、索引或类型转换以及对已映射模板接口的直接调用；`kind=scaffold` 只允许系统 `#include`、命名空间指令、主函数外壳、括号以及空白或纯说明注释。后两类的三个模板字段必须为 `null`，且都不得包含独立算法、数据结构或对参考 solver 的改写。空白和纯注释行并入相邻同职责块；职责变化时必须拆块。规范化该对象所得 SHA256 就是批次身份中的 `mapping_evidence_sha256`。

每次独立复核的证据对象固定为：

```json
{
  "schema_version": 2,
  "problem_id": "<official_category>/<problem_name>",
  "review_id": "<本题唯一复核编号>",
  "source_sha256": "<最终 main.cpp 的 SHA256>",
  "mapping_evidence_sha256": "<逐块映射证据 SHA256>",
  "checks": {
    "complete_source_coverage": true,
    "adapter_and_scaffold_contain_no_algorithm": true,
    "no_reference_solver_code": true,
    "template_blocks_match_template": true,
    "template_hashes_match": true
  },
  "summary": "<独立复核摘要>",
  "conclusion": "matched"
}
```

五项检查必须全为 `true`。规范化每个复核对象得到其 `evidence_sha256`；批次身份中的 `review_id`、`summary` 和 `conclusion` 必须与该证据对象逐字一致。提交前报告必须打印三类实际使用的规范化证据对象及其哈希，不能只打印占位 schema。

`receipt.path` 固定相对于本目录，单题批次使用 `.local/scoped-receipts/<problem>.json`，全量审计使用 `.local/yosupo-local-verification.json`；所有其他路径也使用仓库相对 POSIX 形式，大小写严格沿用 manifest 或磁盘中的规范名称；所有 SHA256 都使用 64 位小写十六进制。集合型数组使用 Python 字符串的 Unicode 码点升序：`official_categories` 按分类名，单元素 `problems` 以 `problem_id` 校验唯一身份，`tools`、`template_inputs`、`references` 和生成证据的 `inputs` 按 `path`，`reviews` 按 `review_id`，映射 `blocks` 按整数 `start_line` 排序；各自排序键必须唯一，发现重复就拒绝生成批次。`argv` 是有语义顺序的数组，保持执行顺序，绝对不能排序。`manifest_sha256` 对解析后的 `manifest.json` 使用下一段相同的规范化 JSON 方法计算；覆盖矩阵、收据、工具、源码、逐题元数据、模板输入和参考文件的 SHA256 都直接对文件原始字节计算。不得加入时间、耗时、内存波动或绝对路径等不稳定字段。

批次 JSON、最终单题结果对象和上述三类来源证据对象都使用 `json.dumps(obj, ensure_ascii=False, sort_keys=True, separators=(",", ":"))` 序列化为 UTF-8 无 BOM、无末尾换行的字节串，再计算 SHA256。报告中必须同时打印实际规范化 JSON、实际证据对象和各自摘要，使线上阶段能够从磁盘与来源证据重新生成同一字节串。批次报告是覆盖矩阵的派生输出，直接输出到当前任务报告；如工具需要临时落盘，只能使用独立系统临时目录并在本题结束后清理。发送前不得把它追加到 `coverage_audit.path` 指向的文件，也不得用包含自身批次 JSON 的文件作为 `coverage_audit`，从而避免哈希自引用。来源映射、生成命令或参数、生成比对结果、生成工具、复核证据、复核结论、逐题元数据或覆盖矩阵任一变化都会改变批次摘要；审批模式下旧批准随即失效，默认直接提交模式也必须重新验证并生成新报告。报告结尾按授权模式写成以下之一：

```text
状态：direct_authorized
批次：<batch_sha256>
尚未在线提交：<official_category/problem_name>；全部技术门禁已通过，将按默认授权提交该题并等待最终判定。
```

```text
状态：approval_pending
批次：<batch_sha256>
尚未在线提交：<official_category/problem_name>；用户已要求本范围提交前确认。若同意，请明确回复“同意提交批次 <batch_sha256>”。
```

默认模式下，报告进入 `direct_authorized` 后无需等待用户回复，执行者应继续逐题在线提交，不能把报告本身当成暂停点。只有用户明确要求审批的范围才使用 `approval_pending`；含糊的偏好或此前某次审批不能自动扩大到其他章节、批次或题目。审批只允许该摘要对应的题目和文件各提交一次；任何代码、清单、测试、工具、依赖、映射、覆盖矩阵或官方题库变化都会产生新摘要并使旧批准失效。无法确认明确的审批要求是否覆盖当前范围时必须询问；没有明确审批要求时按默认直接提交执行。

现有脚本不会自动判断用户是否为当前范围设置了审批要求，这一模式门禁必须由执行者主动核对保证。

## 九、授权判定后的在线提交

进入 `direct_authorized` 或取得当前单题批次明确批准后，先冻结工作区，重新计算批次摘要并确认收据仍有效；不一致时停止，不允许提交。章节可以连续推进多题，但每题都要在前一题结果写回后重新生成自己的单题批次；不存在覆盖多题的批次摘要或一次性批次批准。高风险题包括修改了算法或复杂度、影响共享底层组件、依赖人工来源证明、边界条件敏感或本地性能接近时限的题目；章节的第一道高风险题作为 canary，取得当前 `online_ac` 后才处理下一题。

当前提交脚本没有经过验证的 fail-fast 批量模式，因此每次命令只能包含一个题目。第 03 章 `data_structure` 题还必须给出当前单题批次：

```powershell
python library-checker-template-solutions/tools/submit_yosupo.py --submit `
  --only <单个已通过门禁的第 03 章题目名> `
  --batch .local/ch03-batches/<problem>.json `
  --jobs 1
```

其他章节不接受 `--batch`，以绑定当前题的 scoped receipt 单题提交：`--only <单个已通过门禁的题目名> --receipt .local/scoped-receipts/<problem>.json --jobs 1`。

每题发送前都重新确认当前批次摘要、该题源码哈希、技术门禁和授权模式仍然有效；发送后必须等待最终 verdict，并核对题目、语言、`is_latest` 和服务端回显源码 SHA256。只有该题进入 `online_ac`、在线结果按第八节写回并生成最终单题报告后，才能为下一题生成新批次并启动其单题命令。任一题出现非 AC、哈希不符、状态未知或工具异常时立即停止，不能发送本章的后续题目。即使同章有多题分别进入 `direct_authorized` 或分别获批，也禁止在线阶段使用多题 `--only` 或 `--all`；只有将来脚本实现并测试了真正的 fail-fast 后，才能另行修改本规范。

`--jobs 1` 只保证脚本内部串行，不是 fail-fast。提交器必须原样发送报告哈希对应的 `main.cpp`；`SUBMITTED`、本地通过、旧 AC、参考 AC 都不能记录成当前源码 AC。

若请求可能已到达服务器但没有返回提交编号，立即进入 `submission_unknown` 并停止整个批次。先按题目、发送时间窗口和源码 SHA256 查询近期提交：找到唯一匹配项后记录其提交编号，转为 `submitted` 并等待该编号的最终结果；找不到或存在多个候选时保持 `submission_unknown`，不得重交。确需重试时，先向用户报告原请求、查询范围、歧义和风险，并重新获得“允许该批次该题再提交一次”的明确批准；原批次的一次性批准不能自动覆盖这次重试。

## 十、失败与调优闭环

线上 CE、WA、RE、MLE、TLE 或性能回退不是章节或全章节任务的终点。它只阻断当前题之后的在线发送；执行者必须持续完成当前题的闭环，直到取得同一份当前模板生成源码的 `online_ac`，然后才可处理下一题。不得把失败题标为“待以后处理”、以历史 AC 或参考 AC 代替，或跳过到同章其他题。

对每次可确认的失败，按以下顺序强制执行：

1. 保留提交编号、最终 verdict、时间、内存、当前及服务端源码 SHA256，并把失败源码与当前源码的关系写入 `meta.json`；
2. 完整复查官方题面、生成器、checker、官方/受控参考和模板真实调用链，逐项比较数学不变量、渐进复杂度、热点调用次数、分配、数据布局和 I/O；
3. 给出可复现的数学原因或同环境实测原因。TLE 必须至少覆盖触发数据分布与时限，不能仅以“机器较慢”解释；
4. 任何模板、Markdown、头文件或测试修改前，完整阅读 `hushuqi算法竞赛模板/编写规范.md`；随后在 Markdown 权威模板、同步头文件和开发期回归中一并修复，不得只改题目目录的 `main.cpp`；
5. 加入能重现本次错误或性能退化的最小回归。TLE/MLE 额外加入贴近官方最大约束的可重复压力测量，并同时核对答案；
6. 重新生成当前唯一 `main.cpp`，重建 `manifest.json`/`meta.json`，完成源码级来源核验、本地正确性、官方 checker 和性能收据；
7. 在默认直接提交授权下原样重新提交新 SHA256 并等待最终 verdict；仍非 AC 时从第 1 步继续。只有 `submission_unknown` 的不确定重交保留既有的显式许可要求。

- CE：回到模板依赖和独立生成过程，修模板或生成规则并增加编译回归。
- WA：回到数学、前置条件、边界和参考实现逐函数对照，修模板并增加最小复现。
- RE/MLE：检查模板的数据结构、下标、递归深度、生命周期和峰值内存。
- TLE 或 AC 但显著更慢：重新比较算法复杂度、变换次数、分配、布局、取模和 I/O。若找到复杂度更优实现，按“多实现保留与替换”规则判断：旧版仍适合小约束、不同前提或更易调用时，保留并新增高性能版本；仅在旧版被严格支配时替换。无论哪种结论，都要新增覆盖两版边界语义的测试，并让 LC 候选调用满足官方上限的版本。
- 已知提交编号时网络、排队或轮询超时：保持 `submitted`，继续查询同一次提交，不立即重交。
- 未知提交编号且请求可能已发出：进入 `submission_unknown`，按题目、时间和源码哈希核对近期提交；查不清时停止，任何重试都要重新获得明确批准。

任何模板、源码、测试、清单、工具、依赖、LC 映射、覆盖矩阵或官方题库修正都会产生新批次摘要，必须重新执行“模板审阅或修改 -> 独立生成与清单登记 -> 本地正确性 -> 性能 -> 报告 -> 授权模式核对”。默认直接提交模式在新摘要重新通过全部门禁后继续逐题提交；用户明确要求审批的范围则必须重新等待新摘要批准。

## 十一、本地状态整理与中断恢复

`library-checker-template-solutions/.local/` 是受控的本地状态根目录，不是无差别缓存。任务开始、中断恢复和章节结束时都要按下列分类检查；清理前先确认没有对应活进程，且只能删除明确属于本次工具的精确路径。

- 必须保留：`library-checker-problems/` 固定 commit 工作树、`yosupo-profile/` 持久登录态、当前 `yosupo-local-verification.json`、仍被流程或审计引用的 `scoped-receipts/`，以及当前源码对应的 `ch03-performance/`、`ch03-batches/`、`ch03-pre-meta/` 和 `ch03-results/`。它们是可重算的本地证据，不是第二份题解源码。
- 可以删除：已结束命令的 `.out.log`/`.err.log`、一次性登录辅助脚本、`__pycache__/`、已确认不再被任何当前批次或审计引用的诊断收据，以及明确属于已退出任务的系统临时构建目录。不能用通配符清理整个用户临时目录。
- 不得删除：任何 `main.cpp`、`meta.json`、`manifest.json`、覆盖矩阵、参考目录、用户模板、性能/批次/结果证据或受控 profile；它们即使未被 Git 跟踪，也可能是后续审计和线上哈希核验的输入。

每次清理要在任务记录中说明“保留什么、删除什么、为何可删除”；清理后重新检查 Git 状态和 `.local/` 清单。若某路径的用途或归属无法从流程、引用关系和时间窗口确定，则归类为待保留，不能以“上次中断”推断它可以删除。

## 十二、完成标准

单题只有同时满足以下条件才算完成：

1. 官方题面、checker、参考实现和模板真实调用链已经逐行复查并留下结论；
2. 已用参考实现审视模板的数学、边界、复杂度和常数，发现的缺项或问题均先按编写规范订正用户模板并增加测试；若确实无需修改，必须记录 `template_unchanged` 的逐项依据，禁止为了制造“有改动”而做无意义修改；
3. 已从审阅后的当前模板生成唯一自包含 `main.cpp`，同步生成 `meta.json` 并加入 `manifest.json`；
4. 独立源码来源可追溯，哈希、manifest、meta 和本地收据一致，正确性与性能门均通过；
5. 授权模式正确：默认范围为 `direct_authorized`，用户明确要求审批的范围具有当前批次有效批准；
6. 已发生真实 LC 在线提交，服务端最终 verdict 为 `AC`、`is_latest=true`，回显源码哈希与当前磁盘源码一致；
7. 构建使用独立系统临时目录并保证异常退出清理，最终扫描确认临时源码、可执行文件、缓存和重复目录均已清理；`.local/` 中规定保留的官方题库、浏览器状态和当前收据不属于待删缓存；
8. 最终报告明确区分 `local_verified`、`submission_unknown`、`submitted`、`online_ac` 和失败项目；存在 `submission_unknown` 的题目不能报告完成。

一个章节只有在单题标准之外再同时满足以下条件才算完成：

1. 覆盖矩阵与冻结 commit 下该章最终覆盖集合逐项一致，即主责分类全集与 `93-其他分类审计.md` 分配给本章的题各有且仅有一行；
2. 没有 `review_pending`、`reference_gap`、`template_gap`、`template_change_required`、`source_gap` 或 `tool_gap`，该章节覆盖矩阵每一行都恰好对应一份当前候选，不能用全局 manifest 的其他章节候选补足数量；
3. 每行均完成“参考实现驱动的模板审视与订正 -> 从当前模板生成并登记 LC 单文件 -> 本地验证 -> 真实在线提交”的闭环；
4. 每行当前状态均为 `online_ac`，并记录提交编号、最终 verdict 和服务端源码哈希；
5. 模板专属且在本章最终官方覆盖集合中没有独立映射的条目仅列在 `not_applicable` 表中，不得用来抵消或替代任何官方题；正文明确复用的条目另列共享覆盖，跨章对应关系按主责章节记录。

因此，“章节正文和测试已复查”“头文件全部能编译”“当前 manifest 没有该章候选”都不能单独构成章节完成。缺少任一项时只能报告当前实际进度，不能写成“本章已经完成 Library Checker 复查”或“本章没有可提交 LC 代码”。
