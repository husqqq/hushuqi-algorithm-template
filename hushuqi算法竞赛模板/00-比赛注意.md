# 0. 比赛注意


## 0.1 卡题

不要急。通过队伍多的题不一定难，不要一开始就把题目想得过于复杂。

1. 重新仔细阅读题面，思考每个可能有用的条件，尤其是数据范围。
2. 尝试倒着思考，从目标状态或答案反推必要条件。
3. 在题单上写下已有想法，整理已经确定的结论和仍待验证的分支。
4. 寻求队友帮助时直接说明卡住的具体位置，不要只转述题意。
5. 觉得思路正确时多测试几个样例，优先补充边界情况。

## 0.2 提交前

恭喜你马上要通过这一题了，但不要因为样例正确就放松检查。

1. 手算至少 3 组样例，必须包含边界情况；这通常花费不到 5 分钟，不要省略。
2. 检查需要初始化的变量和数组大小。
3. 重新估算时间复杂度和空间复杂度，确认还有没有可优化的部分。
4. 删除调试输出和临时断言。
5. 提交代码。
6. 打印代码前再确认提交的是最后修改并验证过的版本。

## 0.3 AC

恭喜，通过后去看下一题；若这份代码以后要写入模板，再补充边界测试和接口说明。

## 0.4 WA

能通过样例只说明代码距离正确不远，不能说明实现已经覆盖所有情况。

1. 手算至少 5 组样例，必须包含边界情况。
2. 检查是否会溢出 `long long` 或 `__int128` 的取值范围。
3. 检查所有需要初始化的变量。
4. 删除调试信息，确认调试分支不会影响提交代码。
5. 检查数组的行列含义是否写反。
6. 检查排序方向是从小到大还是从大到小，严格与非严格关系是否一致。
7. 检查输出格式是否匹配题面，包括前导零、空格、换行和精度。
8. 使用随机数据进行多组对拍，缩小到最小反例。
9. 重新读一遍题意，逐句确认自己的理解没有遗漏。
10. 让队友根据题面独立构造几组样例。
11. 使用小黄鸭调试法，逐行解释代码并重点检查变量名是否写错。

## 0.5 TLE

程序已经接近正确时，先排除实现死循环，再确认复杂度和数据规模。

1. 优先检查是否存在死循环、递归不收敛或队列没有及时清空。
2. 重新核对复杂度，确认最坏情况而不是平均情况能够通过。
3. 检查读入数据的格式和题目约定是否一致，避免把错误输入当成算法瓶颈。
4. 评估能否用线性数据结构替代 `map`、`set` 等对数结构。
5. 删除调试输出。
6. 识别可以预处理的量，避免在每次查询或每个状态中重复计算。
7. 使用小黄鸭调试法，逐行检查循环边界、状态转移和变量名。

## 0.6 RE

运行时错误通常来自越界、非法数学运算或资源使用不当。先根据错误类型缩小范围。

1. 检查数组是否开小，所有下标是否满足题面和实现的边界。
2. 检查是否存在除以零、对负数开平方等非法运算。
3. 检查输入格式是否和题目匹配，读入失败后是否继续使用了无效数据。
4. 检查数组是否开得过大；内存超限有时会以 RE 的形式返回。
5. 检查循环边界和递归终止条件。
6. 使用小黄鸭调试法，逐行检查变量名、引用和指针是否写错。
